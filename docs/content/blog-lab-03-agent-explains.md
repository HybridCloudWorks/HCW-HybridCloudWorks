`terraform init` ends by telling you what to do next:

```text
Terraform has been successfully initialized!

You may now begin working with Terraform. Try running "terraform plan" to see
any changes that are required for your infrastructure. All Terraform commands
should now work.
```

That is real output, from the terraform inside the sandbox template this part
builds, run against the landing zone from [part 1](https://hybridcloudworks.com/azure/blog/build-a-landing-zone-you-can-read).
It is also the one suggestion the agent in that sandbox is told never to take,
and never to pass on to you.

This part opens the folder in a Docker sandbox with Claude Code, terraform and
the Azure CLI inside, asks the agent to explain the hub and validate the files,
and then reads the short file that sets its rules: `AGENTS.md`.

The build is still the one from part 1:

```landing-zone
lz=mg,policy,mgmt,hub&corp=0&online=0
```

## What you'll have at the end

| Piece | Result |
| --- | --- |
| A sandbox template, `hcw-lz-sandbox:v1` | Docker's Claude Code template plus terraform 1.16.4, the Azure CLI 2.90.0 and `AGENTS.md`, built from the repository |
| A sandbox named `hcw-lz` | A microVM on your machine with the part 1 folder mounted and nothing else, allowed four hosts beyond the agent's own |
| An explanation you can check | The agent's account of `connectivity.tf`, and what `init`, `fmt -check` and `validate` printed |

## What it costs

**Local sandboxes are free.** The agent's model usage runs on your own Anthropic
API key or Claude subscription, not on this site. The template takes 3.38 GB of
disk, 2.4 GB of it Docker's base image.

Cloud sandboxes (`sbx --cloud`) are a different arrangement: they bill your own
Docker subscription, cannot mount a folder from your machine, and expire after
an hour by default. Everything below is local.

## Why a sandbox, and why AGENTS.md

### A microVM with one folder, not your terminal

The obvious way to ask an agent about a folder is to open a terminal in it and
start one. That agent can see everything you can: your `az login`, your other
repositories, your credentials. For a folder whose whole point is that it is
never applied, that is the wrong neighbourhood.

A Docker sandbox runs the agent in a microVM on your own machine, with the
folder you name mounted inside and nothing else.

This matters more than it sounds, because the agent in Docker's Claude Code
template does not stop to ask before it runs a command. Once the template is
built in step 1, its default command says so.

PowerShell:

```powershell
docker image inspect hcw-lz-sandbox:v1 --format "{{json .Config.Cmd}}"
```

bash:

```bash
docker image inspect hcw-lz-sandbox:v1 --format "{{json .Config.Cmd}}"
```

```text
["claude","--dangerously-skip-permissions"]
```

So the boundary cannot be a prompt asking permission. It is the environment:
one folder, no credentials, and a network that allows almost nothing.

### A network with four holes in it

A local sandbox's outbound traffic is denied by default, and the built-in
`claude` kit allows Anthropic's endpoints and nothing else. `terraform init`
needs four more hosts: `registry.terraform.io` and `releases.hashicorp.com` for
the providers, `github.com` and `codeload.github.com` for the Azure Verified
Modules. Step 3 allows exactly those, for this sandbox only.

Nothing on that list is an Azure endpoint.

### AGENTS.md: what the agent is told, and why apply is on the wrong side of it

The template installs one file as the agent's briefing, at
`~/.claude/CLAUDE.md` where Claude Code reads it in every session, with a copy
at `~/AGENTS.md` for you. It tells the agent the folder is a landing zone
generated for learning, has it run `terraform init -backend=false`,
`fmt -check` and `validate`, and asks it to explain the files. Then:

> Never run `terraform apply`, `terraform plan`, `terraform destroy` or
> `terraform import`, with or without `-backend=false`, and never suggest the
> learner runs them here. A plan needs credentials to a real tenant; this
> sandbox has none and this folder is not meant for one.

Three reasons sit behind that rule, and the order matters.

**The folder is not meant for a tenant.** The first line of `terraform.tf`
says so — "Generated by the HybridCloudWorks Landing Zone Builder for learning.
Never applied here." — and the README says it again. The subscription ids in
`terraform.tfvars.example` are `00000000-0000-0000-0000-000000000001` and
`00000000-0000-0000-0000-000000000002`: placeholders, not defaults.

**A plan is where credentials start.** `validate` reads files. `plan` reads the
tenant, and needs credentials the sandbox does not have. An agent whose plan
fails goes looking for what is missing, which is why the next rules in the file
close that road too: never run `az login` or any `az` command that reads or
changes a subscription, never write real subscription ids, tenant ids or
secrets into the files, and never ask the learner for any. `plan` is on the
list with `apply` for that reason, not because it changes anything.

**The instruction is not the only guard, and should not be.** A file an agent
reads is guidance, and guidance can be misread. What actually stops `apply`
here is that there is nothing to apply *with*: no credentials in the sandbox,
and no Azure endpoint on its allowlist. AGENTS.md makes sure the agent does not
spend your session trying, or talk you into trying for it.

One more rule is worth copying into your own agent files:

> Never change the module versions or provider constraints to "make it work";
> report what fails and why.

An agent that pins around a failure hides the one thing you were trying to
learn.

- The part 1 folder: `landing-zone.zip`, unzipped to `landing-zone`.

## The steps

### 1. Build the template

From the root of the clone:

PowerShell:

```powershell
docker build --platform linux/amd64 -f lab-image/sandbox-template/Dockerfile -t hcw-lz-sandbox:v1 lab-image
```

bash:

```bash
docker build --platform linux/amd64 -f lab-image/sandbox-template/Dockerfile -t hcw-lz-sandbox:v1 lab-image
```

The build context is `lab-image`, not the template's own directory, so the
Dockerfile reads terraform's and the Azure CLI's versions from `versions.env`,
the same file the part 2 image is built from. `--platform linux/amd64` because
the checksums in that file are for amd64.

**Verify:** the build ends with `naming to docker.io/library/hcw-lz-sandbox:v1`,
and `docker image ls hcw-lz-sandbox` shows one row of about 3.38 GB.

### 2. Hand it to the sandbox runtime

The sandbox runtime keeps its own image store, so `docker image ls` showing the
template does not mean `sbx` can see it. Save it, then load it.

PowerShell:

```powershell
docker image save hcw-lz-sandbox:v1 -o hcw-lz-sandbox.tar
```

```powershell
sbx template load hcw-lz-sandbox.tar
```

bash:

```bash
docker image save hcw-lz-sandbox:v1 -o hcw-lz-sandbox.tar
```

```bash
sbx template load hcw-lz-sandbox.tar
```

**Verify:** `sbx template ls` lists `hcw-lz-sandbox:v1`.

### 3. Open four hosts for this sandbox

PowerShell:

```powershell
sbx policy allow network --sandbox hcw-lz "registry.terraform.io:443,releases.hashicorp.com:443,github.com:443,codeload.github.com:443"
```

bash:

```bash
sbx policy allow network --sandbox hcw-lz "registry.terraform.io:443,releases.hashicorp.com:443,github.com:443,codeload.github.com:443"
```

The rule names the sandbox before it exists and applies when it is created, so
the name here and the name in step 4 have to match.

**Verify:** `sbx policy ls hcw-lz` shows the four hosts.

### 4. Create the sandbox in the folder

Change into the `landing-zone` folder, then run the same text in either shell:

PowerShell:

```powershell
sbx run --name hcw-lz --template hcw-lz-sandbox:v1 claude .
```

bash:

```bash
sbx run --name hcw-lz --template hcw-lz-sandbox:v1 claude .
```

`sbx run` creates the sandbox the first time and reattaches after that. The
folder is mounted inside at the same absolute path it has on your machine.

**Verify:** Claude Code opens, in the folder.

### 5. Ask for the explanation and the checks

Paste this first:

> Explain what this landing zone deploys, then run terraform init
> -backend=false, terraform fmt -check and terraform validate and tell me what
> each printed.

Then the hub:

> Explain connectivity.tf: what the hub creates, which module and version it
> calls, and why the firewall is off.

**Verify** against what the tools print, not against how sure the agent
sounds. Run in this image against this folder, the three commands print:

- `terraform init -backend=false`: six providers installed, each
  `signed by HashiCorp` or `signed by a HashiCorp partner`, then
  `Terraform has been successfully initialized!` and the paragraph at the top
  of this post.
- `terraform fmt -check`: nothing at all. No file listed means every file is
  already formatted.
- `terraform validate`: `Success! The configuration is valid.`

If the agent's summary differs from that, ask it to paste the output rather
than describe it.

### 6. Check the explanation against the file

`connectivity.tf` is 49 lines. An account of the hub is right when it matches
them:

| The file says | So the explanation should say |
| --- | --- |
| `source = "Azure/avm-ptn-alz-connectivity-hub-and-spoke-vnet/azurerm"`, `version = "0.17.5"` | That module, at that version |
| `name = "rg-alz-connectivity-${var.location}"` | One resource group for the hub, named from the region |
| `default_hub_address_space = var.hub_address_space`, default `10.0.0.0/16` | The hub's address space, and where to change it |
| `bastion`, `private_dns_zones`, `private_dns_resolver` and `dns_resolver_policy` all `true` | Bastion, the Private Link DNS zones and a DNS resolver live in the hub |
| `firewall = false`, `firewall_policy = false` | No firewall, and the file's own reason: "spokes egress directly until the firewall component is added" |
| Both gateways `false`, and `ddos_protection_plan = false` | No ExpressRoute or VPN gateway yet, and no DDoS plan, because it is "a fixed monthly charge" |

Then ask it something the files cannot answer:

> What will this cost per month?

The files hold no prices. AGENTS.md says "When a question needs a fact the
files do not hold, say so rather than guess", and an answer that opens with a
number has not followed it.

### 7. Leave it

Detach with `Ctrl+\`. When you are finished with the sandbox:

PowerShell:

```powershell
sbx rm hcw-lz
```

bash:

```bash
sbx rm hcw-lz
```

## How to know it worked

- `validate` printed `Success! The configuration is valid.` and `fmt -check`
  printed nothing, in the output the agent pasted and not only in its summary.
- The account of the hub matches the table in step 6, the missing firewall
  included.
- Asked for a monthly price, the agent said the files do not hold one.
- Asked to run `terraform plan`, the right answer is a refusal that says why.
  That is the file working. If it tried anyway, there is nothing for it to use:
  no credentials, and no Azure endpoint it may reach.

## When it doesn't work

**`sbx template ls` does not list the template you just built.** `docker image
ls` does, and that is the trap: the sandbox runtime has its own image store,
and a successful `docker build` puts nothing in it. Run step 2.

**`terraform init` in the sandbox cannot reach `registry.terraform.io` or
`github.com`.** The network rule is missing, or names another sandbox. From
inside, that reads like a registry outage; it is the sandbox's network policy
doing its job.
`sbx policy ls hcw-lz` should show the four hosts, and the name in the rule
must be the same string as the `--name` in `sbx run`; a rule for `hcw-lz` does
nothing for a sandbox called anything else.

**The agent explains a firewall that is not there, or a version the file does
not pin.** It is answering from what landing zones usually contain rather than
from these files. Point it at the evidence: ask it to quote the
`enabled_resources` block of `connectivity.tf` and answer again from that.

**You want to run this in `sbx --cloud`.** A cloud sandbox cannot mount a
folder from your machine, so the files have to be transferred in or cloned
inside it, and the template has to be loaded into the cloud registry. That path
has not been exercised with this recipe, so it is not written up here.
